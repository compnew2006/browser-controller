# خطة الإصلاح: Smart dedup (liveness-based) لمنع تدمير العمليات الشقيقة

## التشخيص النهائي (مؤكد بالكود + اللوج)

**السبب الجذري:** منطق الـ dedup في `daemon.ts:221-226` بيدمّر **أي** اتصال بنفس `agentName` كل ما اتصال جديد يوصل — بدون ما يتأكد إذا الاتصال القديم لسه حي. ده مصمّم لسيناريو IDE respawn (Cursor بيعمل ده كتير)، **لكن** لو 3 عمليات MCP شغّالة بالتوازي بنفس الاسم (زي Zcode)، كل واحدة بتدمّر التانية → **سباق تدمير متبادل مستمر** (اتأكدت من اللوج: `replacing stale client s2 → s3 → s4 → ...`).

**المنطق المتضارب:** الـ `close` handler (سطر 279-285) **صحيح** بالفعل — بيحرر tab locks فقط لو مفيش اتصال تاني حي بنفس الاسم (`stillAlive` check). المشكلة بس في الـ dedup at `hello`.

## خطة الإصلاح (ملف واحد + اختبار)

### التغيير: `mcp-server/src/daemon.ts` (سطور 221-226)

**الحالي** (يدمّر كل الاتصالات بنفس الاسم):
```ts
for (const [existingSocket, existing] of this.clients) {
  if (existing.agentName === name) {
    console.error(`[...] replacing stale client ${existing.sessionId} (${name})`);
    existingSocket.destroy();
    this.clients.delete(existingSocket);
  }
}
```

**الجديد** (liveness-based — يدمّر فقط الاتصالات half-dead، ويسمح للحيّة بالتعايش):
```ts
for (const [existingSocket, existing] of this.clients) {
  if (existing.agentName !== name) continue;
  const stale = existing.missedPongs >= HEARTBEAT_MAX_MISSED;
  if (stale) {
    console.error(`[...] replacing dead client ${existing.sessionId} (${name}, ${existing.missedPongs} missed pongs)`);
    existingSocket.destroy();
    this.clients.delete(existingSocket);
  } else {
    // Live sibling: allow multi-instance (each gets unique sessionId).
    // The popup already lists each by sessionId. The close handler's
    // stillAlive check already releases locks only on true agent exit.
    console.error(`[...] co-existing session ${existing.sessionId} (${name}, missedPongs=${existing.missedPongs}) — new connection accepted as ${client.sessionId}`);
  }
}
```

**النتيجة:**
- ✅ **IDE respawn محفوظ:** لو الاتصال القديم ميت (missedPongs >= 3، ~45 ثانية بدون رد)، يتدمر ويتم استبداله (نفس سلوك القديم).
- ✅ **multi-process fixed:** لو 3 عمليات Zcode شغّالة، كل واحدة بتعيش (missedPongs=0 لكل واحدة بترجع pong)، وكل وحدة تأخذ sessionId فريد.
- ✅ **tab locks محفوظة:** الـ `close` handler لسه بيحرر locks فقط لو مفيش `stillAlive` sibling — دلوقتي ده بيعمل الصح لما multi-instance متاح (LOCKS تفضل للعمليات الشقيقة الباقية).

### الاختبار: `tests/daemon.test.ts`

### النوافذ المنبثقة (اختياري، صفر كود)
الـ popup مبيعرضش ميزة "multi-session" — دلوقتي لو فيه sessions متعددة بنفس الاسم، كل واحد بـ sessionId فريد (موجود في `agents()`). سأترك ده كما هو (كل صف = session) لأن التغيير مش هيأثر على readability. لو عايز grouping لاحقًا، ده scope منفصل.

## لماذا هذا آمن (Phase 4)

- **التوافق مع الإصدارات السابقة (Backward compatible):** سيناريو IDE respawn لسه شغّال (الاتصال الميت = missedPongs عالي = يتدمر).
- **مفيش zombie accumulation:** الـ heartbeat لسه بيقتل أي اتصال dead بعد 45 ثانية تلقائيًا — ده الـ safety net الأساسي، مش الـ dedup.
- **الـ close handler لسه صح:** الـ `stillAlive` check (سطر 280-282) بيشوف أي اتصال حي بنفس الاسم، فـ tab locks تتدمر فقط لو **كل** العمليات بنفس الاسم ماتت.
- **معرّف (ID) فريد لكل session:** الـ `sessionId` بيكبر monotonically (`s1, s2, s3...`) — مفيش collision.
- **graphify affected** للـ `handleConnection` (الـ method الوحيدة المعدّلة): callers = خادم الـ IPC loop، التغيير داخلي.
