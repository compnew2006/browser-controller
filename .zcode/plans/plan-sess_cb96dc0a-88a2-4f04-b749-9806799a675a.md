# الخطة: إيقاف launchd — MCP client يصبح المسؤول الوحيد عن الـ daemon

## التشخيص النهائي (مؤكد بالكود + اللوج)

**السبب الجذري للـ kill loop:** جهتين بيبدوا الـ daemon بالتوازي بدون ما يعرفوا ببعض:
1. **launchd** (`~/Library/LaunchAgents/com.noiemany.browser-controller.plist`) — `KeepAlive=true` يعيد بدء الـ daemon إذا مات
2. **كل MCP client** (`index.ts main()` → `spawnDaemon()`) — لو `daemonLooksAlive()` رجعت false، يبدأ daemon جديد

### آلية الـ kill loop (مؤكدة من اللوج — 80 restart)
```
1. launchd يبدأ daemon A على :7225                              ✅
2. عميل Zcode جديد يبدأ → daemonLooksAlive() ترجع false (race: IPC socket لسه ما اتعملش) → spawnDaemon()
3. daemon B (الـ spawned) يحاول bind على :7225 → EADDRINUSE
4. daemon B يجري killStaleProcess → probe /pair على daemon A
   - probe فشل (daemon A لسه في مرحلة الإقلاع، /pair مش جاهز بعد)
5. daemon B يقتل daemon A بـ SIGTERM                            ❌
6. launchd يلاقي daemon A مات → يعيد تشغيله بعد ThrottleInterval=10s
7. الـ client اللي بدأ daemon B بيتصل بـ daemon A الجديد (لأن IPC socket ظهر)
   ← daemon B بقي بدون عمل (orphan) → بيموت من EADDRINUSE Fatal
8. يتكرر نفس السيناريو مع كل عميل Zcode جديد
→ 80 restart، "Extension disconnected" متكررة، ERR_CONNECTION_REFUSED عابرة
```

## الحل (قرار المستخدم: launchd out)

المستخدم اختار: **launchd out — MCP client هو المسؤول الوحيد عن بدء الـ daemon**.

ده بيلغي التعارض من جذره: مصدر واحد للحقيقة. الكود الحالي مصمّم فعلاً لده (`spawnDaemon` + `waitForDaemon` + one-shot respawn على disconnect في `index.ts:371-380`).

## التنفيذ (3 خطوات)

### الخطوة 1 — إيقاف + إزالة الـ LaunchAgent (عاجل — يوقف الـ kill loop فوراً)
```bash
launchctl unload ~/Library/LaunchAgents/com.noiemany.browser-controller.plist
# (نحتفظ بملف الـ plist في مكانه مش محذوف — لو المستخدم عايز يرجّعه يدويًا.
#  بس unload يكفي لإيقاف KeepAlive.)
```
بعدها الـ daemon الوحيد الشغّان هيتحدد طبيعيًا (آخر daemon spawn-ed من أي MCP client)، والـ kill loop هيوقف.

### الخطوة 2 — تحسين `daemonLooksAlive` في index.ts (دفاع عميق)
المشكلة الحالية: `daemonLooksAlive()` بتعمل connect-probe 250ms على IPC socket. لو الـ daemon شغّان بس **IPC socket لسه ما اتخلقش** (أواردنغ ordering)، الـ probe بترجع false → client يبدأ daemon منافس.

الحل: **retry قصير قبل ما نقرر spawn**. لو فشل الـ probe الأول، انتظر 300ms وحاول تاني (مرة واحدة). ده بيعطي الـ daemon وقت يخلّص الـ IPC socket bind لو هو فعلاً في مرحلة الإقلاع، وبيمنع الـ redundant spawn.

```ts
async function daemonLooksAlive(): Promise<boolean> {
  // ... existing file + 250ms connect probe ...
  // NEW: if first probe failed but file is fresh, retry once after 300ms
  // (daemon may be mid-startup; IPC socket not yet created)
}
```
**التأثير:** مش هيلغي الـ spawn نهائيًا (مش سيناريو)، بس بيقلل الـ redundant spawns بشكل كبير.

### الخطوة 3 — documentation + التحقق
- أضف note في `agent-config/AGENTS.md` إن الـ daemon بيُدار بواسطة MCP clients دلوقتي (مش launchd)، وإن أي `launchctl unload` سابق لازم يفضل.
- التحقق:
  1. `launchctl list | grep browser-controller` → مفيش output (اتلغى).
  2. شغّل MCP client جديد → لازم يـ join كـ IPC client (مش spawn جديد) لو الـ daemon شغّان.
  3. راقب اللوج لمدة 60 ثانية → مفيش restarts جديدة.
  4. `npm test -- --run` → 174/174 لسه تمُر.

## لماذا هذا آمن
- **بدون إزالة الكود:** مفيش تغيير في الـ daemon logic أو `spawnDaemon`. الكود الحالي مصمّم لـ single-spawner model.
- **`launchctl unload` قابل للعكس:** لو المشكلة رجعت، `launchctl load` بيرجّعه.
- **الـ daemon لسه بيعيش عبر جلسات MCP:** كل client بيعمل `spawnDaemon` لو لازِم، وعنده one-shot respawn على disconnect (`index.ts:371`). مفيش تدهور في الـ uptime.
- **graphify affected** لـ `daemonLooksAlive` = `main()` بس، التغيير داخلي.

## خارج النطاق
- حذف ملف `.plist` (نتركه — المستخدم ممكن يرجّعه لو احتاج).
- تغيير `spawnDaemon` نفسها (مش محتاج — هي المسار الصحيح دلوقتي).
- إضافة managed-mode flag (غير محتاج بعد قرار launchd out).
- إعادة كتابة `killStaleProcess` (الـ logic سليم — المشكلة كانت التعارض، مش الـ probe نفسه).
