# Operations and recovery runbook

This runbook is for a continuously operated, single-host installation. Browser Controller controls a real browser; the daemon, extension, browser profile, network, and target site can fail independently. A running daemon alone does not mean an agent can complete a browser action. Multi-host failover and an availability guarantee are not provided by this repository.

## Monitoring

Run `npm run daemon:health --silent` as the daemon's OS user with the same `BC_STATE_DIR` and built checkout as the service. It prints one JSON object without credentials or agent names. Exit 0 requires an authenticated daemon with the expected PID and at least one connected extension. Exit 1 means the daemon identity could not be verified or the extension is disconnected. `daemon:status` has a different purpose: it reports lifecycle metadata and can fall back to an IPC probe; it is not an end-to-end readiness check.

Configure your existing monitoring system to run this check at an interval agreed by the operator, alert on sustained failures, and alert separately on missing probe results. Choose thresholds based on the required detection time and acceptable transient reconnects; this repository does not install a monitoring agent or send notifications. Record the owner, delivery destination, schedule, and escalation path in your deployment system. Check daemon restart counts, disk space, and log access as separate signals. The health probe does not prove a specific browser profile, tab, website, vault operation, native pairing, or MCP tool call works; add a synthetic end-to-end check against a site and account explicitly provisioned for monitoring if these are service requirements. Never probe production accounts by performing writes.

For a failure, inspect `npm run daemon:status`, the user supervisor's status, and `daemon.log` under the configured state directory. Logs may contain site origins and other sensitive metadata; do not publish them without review. Check Chrome and the extension separately. Do not publish port 7225 or treat the local health check as a remote API. After reconnect, verify the intended browser and perform a safe read against a test page before resuming work.

## State, backup and restoration

Identify and document the exact `BC_STATE_DIR`, service account, browser profile, checkout version, Node version, and extension version before making a backup. The state directory includes credentials, vault keys and stores, memory and site maps, and operational files. Vault recovery snapshots contain the decryption key and can disclose stored accounts. Memory and maps can reveal browsing information. Protect all copies with restricted access and encryption, define retention and deletion, and test those controls. Chrome profiles and signed-in site sessions are separate from daemon state; back them up only under the browser and organization's approved procedures. Re-pairing does not restore lost Chrome cookies or site accounts.

To obtain a consistent offline copy, first stop agent clients, disable their automatic daemon start, and stop the **single** owner/supervisor of the daemon. Confirm it is stopped before using your approved backup mechanism on the complete state directory. Do not restore or copy live lock, socket, PID metadata, or log files over a running installation. Record the application version and backup time with the backup, without including secrets in tickets or logs. Restart through the original supervisor and check health. This is an operational procedure, not an automated backup implementation; snapshots on the same disk are not a disaster-recovery strategy.

For a recovery drill, use a separate OS user or isolated machine, disposable browser profile, and a copied backup. Keep the original backup immutable. Stop all test clients and the test supervisor, restore the copy to an isolated state directory with owner-only permissions, and leave runtime lock/socket/PID metadata out. Start the matching built version under the test account. Check daemon health and pairing with the isolated extension, then verify representative memory and vault data using synthetic records. The vault UI provides backup and restore for the vault itself; it does not restore the whole browser or all daemon state. Never test a restore over the only live copy. Capture actual data loss and recovery duration, then agree and document RPO/RTO with the service owner. Do not claim those objectives are met until a representative drill proves them.

If credentials are invalid, retain a protected copy for diagnosis and follow the pairing rotation procedure in `SECURITY.md`; rotation changes pairing secrets and requires a daemon restart. It does not repair corrupt memory or vault data. If an action was in flight during a disconnect, inspect the target before retrying: a failed call can have already taken effect.

## Capacity and release checks

Run the CI checks on supported Node versions and the isolated `npm run smoke:ci` browser roundtrip before release. That smoke injects pairing into a disposable extension and does **not** exercise the native messaging host. A separate integration test connects the extension's pairing logic to a real installed launcher and host with a simulated Chrome API and synthetic state; it does not replace a real Chromium-to-host pairing test. Use a dedicated temporary profile and account for any additional browser checks, and do not run `smoke:real-chrome` against a production session merely to measure health.

`node scripts/map-bench.mjs` prints an isolated in-process map benchmark; it does not test the real browser or an external site. `scripts/memory-bench.mjs` uses a fake extension and isolated state but appends results to the project's baseline file. Record workload, hardware, version, concurrency, sample count, percentiles, failures, and recovery time when benchmarking. These measurements are baselines, not service-level objectives. Define and validate production load, latency, availability, RPO and RTO with the service owner before treating this deployment as production-ready.
