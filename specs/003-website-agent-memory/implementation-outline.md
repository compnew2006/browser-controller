# Website memory implementation outline

**Status:** Draft discussion aid; this is not the reviewed Spec Kit plan or authorization to implement. The feature is proposed as `EVOLVE / CRITICAL` because it can persist and share data from authenticated browser contexts. Root `constitution.md` is proposed, not ratified; existing `AGENTS.md` instructions apply. Follow the repository's specification and plan review gates before implementation. See [spec.md](spec.md) for intended behavior and acceptance scenarios.

## Baseline and design constraints

- One daemon multiplexes authenticated client sessions and forwards browser calls through the extension. The daemon validates wire tool names and invokes vault-aware routing; `browser_batch` runs steps in the client tool layer. See `mcp-server/src/daemon.ts`, `mcp-server/src/wire-tools.ts`, `mcp-server/src/vault/daemon-routing.ts`, and `mcp-server/src/tools/batch.ts`.
- Browser profiles are selected per session. Existing tab ownership, retry rules, cancellation, timeouts, rate limits, vault restrictions, and protocol compatibility must remain intact. Snapshot refs are page-scoped and cannot be durable locators.
- Mnemon is a candidate, not an accepted dependency. Its published entry point opens its database and starts an MCP stdio server, so importing that entry point is not a passive storage API. Its SQLite driver is synchronous. Validate these properties against the exact pinned version during the prototype. [Mnemon entry point](https://github.com/nikitacometa/mnemon-memory-mcp/blob/main/src/index.ts), [package](https://github.com/nikitacometa/mnemon-memory-mcp/blob/main/package.json), and [driver decision](https://github.com/nikitacometa/mnemon-memory-mcp/blob/main/docs/adr/0003-synchronous-better-sqlite3.md).

## Proposed sequence

1. **Review the spec and agree on acceptance limits.** Confirm permitted memory types, activation/consent and management, profile and account scope, retention, authorized read/write actions, and the precise allowlist for page-derived facts. Verified public, non-personal facts may be shared across profiles for the same origin; visit data stays profile-specific and cross-origin sharing remains out of scope. Define numeric resource and latency limits from a baseline and record test environments before judging performance. Resolve material open decisions before the formal plan is approved.
2. **Prototype the storage boundary with isolated synthetic data.** Compare the current daemon without memory against a daemon-owned Mnemon child process over local stdio. Pin a candidate version only in the later authorized prototype, review its license and supply chain, and verify supported Node 20 and 22 plus native dependency availability on supported platforms. Exercise startup, handshake, errors, shutdown, database/WAL handling, and child crash/restart. Do not import the side-effecting CLI entry point into the daemon. Compare with an in-process adapter only if the child-process result warrants it; neither option is approved or proven yet.
3. **Specify and implement narrow daemon-owned contracts.** Define a typed adapter for permitted writes, reads, status, and deletion, with strict validation, bounded inputs/outputs, stable error codes, authenticated session context, and versioned capability behavior. Register public tools through the existing tool layer, route memory operations locally rather than to the extension, and preserve unknown-tool and old-peer behavior. Include IPC/extension handshake impact only when the chosen design changes the relevant contract. Decide explicitly which memory operations are batchable; prove direct calls and permitted batch steps have equivalent policy enforcement.
4. **Enforce privacy before persistence and retrieval.** Start disabled until globally enabled; isolate visit data by verified profile and origin, while sharing only verified public, non-personal facts for the same origin across profiles. Do not expose another profile's visit history or identifying provenance in shared output. Prevent sharing account-specific information when account identity or permission is uncertain. Fail closed if private-window state, profile, origin, or vault protection is unknown. Exclude incognito, vault/protected contexts, credentials, cookies, input values, URL query/fragment, page bodies, and personal data by default. Do not treat ordinary vault redaction as complete detection of private content. Review page-derived fields against an explicit allowlist and test with synthetic data; never send page content or search logs to an external provider by default. User controls must cover global disabling, site exclusion, inspection and deletion.
5. **Capture only observed, eligible events.** A successful navigation can update limited permitted visit metadata; it does not imply that page content was read. Only an already-requested successful read may produce a permitted, bounded fact, after scope and privacy checks. Do not crawl, refresh sites, or use another agent's tab for capture. Preserve source and observation time, deduplicate equivalent observations, record replacement history or provenance, and treat retrieved information as untrusted data that cannot authorize actions. Revalidate live targets before use.
6. **Make writes bounded and recoverable.** Specify queue capacity, write timeout, cancellation, deduplication and overload policy, including whether an update was persisted, dropped, or remains pending; do not promise lossless asynchronous writes without a durable queue. Memory failure or a full queue must not change the browser action result, retry a non-idempotent action, or indefinitely block the daemon. Test concurrent agents, daemon/child shutdown, crash during update, corrupted or unavailable store, and recovery with explicit outcomes.
7. **Verify and review before delivery.** Use isolated fixtures and a synthetic store for unit, contract, daemon integration, concurrency, privacy, recovery and injection tests; include agent A → agent B across sessions and after restart, direct calls and batch, profile/account isolation, revocation and deletion, disabled mode, failures and retries. Run affected regression checks followed by project CI-equivalent `npm run lint`, `npm run typecheck`, `npm run build`, `npm run test:coverage`, `npm run security:audit`, and `npm run context:lint` on Node 20 and 22 as applicable. The audit contacts a package registry and requires the owner's authorization before any such contact; missing runtimes or dependencies also require authorization before installation. Review dependency license and attribution if code is copied. Independently review security and actual diff; report local checks separately from CI and Owner approval. Real-Chrome testing, if later authorized and needed, must use isolated test pages and respect the existing browser profile and daemon lifecycle.

## Prototype measurements and decision record

Measure the same synthetic workload with memory disabled, child process enabled, and any in-process alternative: startup duration; idle and peak memory; memory read/write and browser-call p50/p95/p99; throughput under multiple agents; queue pressure and dropped/timed-out updates; database growth; and recovery time. Record workload, hardware, platform, Node version, sample count and failures. Measure model tokens only if a model is actually used and provider usage is available; otherwise mark `UNAVAILABLE`. FTS-only is the starting candidate; embeddings are not required for the prototype.

**Thresholds:** to be agreed in the reviewed plan after the baseline; no measured result or implementation approval is implied by this outline. A separate-process result that fails privacy, compatibility, resilience, or agreed resource limits must not be promoted merely because it integrates successfully.
