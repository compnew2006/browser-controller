# خطة التنفيذ: ملف معرفة منظم لكل موقع

**Branch**: `main` فعليًا؛ `008-site-knowledge` معرّف ميزة Spec Kit وليس branch موجودة.  
**Date**: 2026-11-04  
**Spec**: [spec.md](spec.md)  
**Status**: مقترحة لمراجعة المالك؛ لا ترخّص التنفيذ أو ترحيل بيانات فعلية.

## Summary

إضافة معرفة عامة منظمة للموقع لكل browser profile، في مخزن مستقل عن Website Memory وSite Map. الإصدار الأول يتيح إدخالًا يدويًا منظمًا والقراءة والبحث والتعديل والحذف والتصدير بعد مراجعة المالك. الاستعادة المُدارة والملخصات المقترحة والاستيراد تُسلَّم لاحقًا على نفس عقد المراجعة. لا تحفظ القراءة أو التصفح معرفة حرة، ولا تُحفظ معلومات حسابات خاصة.

القراءة تخص profile الاتصال المحدد ولا تطلب موافقة مستقلة؛ الكتابة تتطلب معاينة كاملة وموافقة مرتبطة بالمحتوى والنطاق والنسخة، مع إعادة التحقق قبل commit. هذا فصل منطقي للعملاء الموثوقين، وليس sandbox ضد عميل مقترن خبيث أو مالك shell بنفس المستخدم. القرارات في [research.md](research.md).

## Technical Context

**Language/Version**: TypeScript وES modules على Node `^22.18.0 || ^24.11.0 || >=26.0.0`؛ JavaScript في Chrome MV3 عند الحاجة فقط. البيئة التي قُرئت: Node `22.23.1`.

**Primary Dependencies**: المكتبات القائمة `@modelcontextprotocol/sdk` 1.32.2 و`zod` 4 و`ws` 8؛ لا تعتمد الخطة على حزمة أو ترقية جديدة. تأكيد MCP يتطلب عميلًا يدعم form elicitation؛ لا يُفترض أن كل عميل يعرض المعاينة كاملة.

**Storage**: ملفات JSON محلية خاصة بالمستخدم في namespace جديد تحت state directory، بملف مستقل لكل `(browserId, canonical origin)`؛ atomic replace واحد لكل دفعة. ليست مشفرة، ولا تمنع مستخدم النظام نفسه من القراءة. لا تُغيَّر ملفات الذاكرة أو الخرائط الحالية ولا تُرحّل.

**Testing**: Vitest؛ اختبارات schema وsecret fixtures، daemon IPC متعدد العمليات، الموافقة والتزامن، التوافق، استعادة اصطناعية، وMCP client يدعم/لا يدعم elicitation. Chrome معزول لحدود extension؛ smoke الحقيقي لا يُشغَّل على profile المستخدم لمجرد التحقق.

**Target Platform**: daemon محلي أحادي المالك على أنظمة Node المدعومة وChrome extension MV3؛ اختبارات CI المعلنة في `AGENTS.md`. دعم Windows للأذونات والـ named pipe يُختبر في بيئة مناسبة ولا يُستنتج من POSIX.

**Project Type**: MCP server وdaemon محلي وextension وowner CLI اختياري؛ لا خدمة خارجية أو قاعدة بيانات جديدة.

**Performance Goals**: حدود موارد أولية مقترحة: 100 عنصر لكل موقع/profile، 2 KiB UTF-8 لكل عنصر، 128 KiB لكل ملف، 500 ملف لكل profile، و32 MiB إجمالي. الدفعة حتى 8 عناصر وبحد معاينة كامل 4 KiB؛ تُرفض قبل الموافقة إذا تعذر عرضها بالكامل. هذه حدود تصميم مقترحة وليست قياسات إنتاجية أو SLO. يُقاس p95 للبحث والكتابة على fixture عند الحدود وتُوثق النتائج قبل تثبيت هدف زمني.

**Constraints**: تعطيل افتراضي مستقل، حصر النطاق وإعادة التحقق، مراجعة المالك الكاملة قبل mutation، عدم حفظ الأسرار أو الحسابات الخاصة، لا ادعاء بأن الكواشف تكتشف كل الأسرار، عدم تخزين مسودات غير معتمدة أو إرسالها لخدمة خارجية، واستعادة بموافقة بعد تحذير. لا تُطبع النصوص أو معرّفات شخصية في diagnostics.

**Scale/Scope**: تشغيل محلي لمالك واحد وعدة profiles وعملاء مقترنين موثوقين؛ لا multi-tenant service أو HA. حدود الأرقام أعلاه تبدأ صغيرة وتُراجع بأدلة الاستخدام.

**واجهة السياسة والموافقة**: تُدار سياسة الميزة من واجهة المالك المحلية التفاعلية المقترحة في `scripts/memory.mjs`، كما يحدد العقد. P0 يختبر واجهة المراجعة الفعلية ببيانات اصطناعية قبل كتابة الميزة، بما فيها الصفحات المتعددة إن كانت ستستخدم للاستعادة. لا يُستنتج عرض كامل من إعلان elicitation أو عداد صفحات. لا يحمي التصميم من حامل token خبيث، ولا يثبت انتباه المالك؛ إن تعذر إثبات مسار عرض مناسب تُغلق عمليات الكتابة المعنية.

**حالة بوابة P0:** وافق المالك صراحةً في جلسة التنفيذ على الخطر المتبقي لاحتمال عدم اكتشاف سر في النص الحر. لم يُثبت بعد عرض العميل الفعلي للمعاينة الكاملة. يجوز تطوير الكود واختباره ببيانات اصطناعية في بيئة معزولة قبل T070؛ لا يجوز تمكين الحفظ الحقيقي أو تسليم الميزة للاستخدام قبل نجاحه. تبقى واجهات الميزة الحقيقية غير مسجلة أو ترفض الكتابة افتراضيًا حتى تتوفر واجهة مؤهلة ويُختبر ربطها بمسار الاعتماد الفعلي؛ لا يكفي متغير بيئة أو تصريح من الوكيل لتجاوز البوابة. فحص المصدر يُظهر أن القناة الحالية تتحقق من قدرة `elicitation.form` وتستقبل تأكيدًا، لكنه لا يثبت عرض رسالة كاملة على واجهة العميل. أُعد خادم اختبار اصطناعي مستقل وتعليمات تشغيل مؤقتة في `quickstart.md`؛ فحص بروتوكول SDK بعميل اختباري نجح للقبول والإلغاء وغياب القدرة، لكنه ليس فحص واجهة فعلية ولا يعني نجاح T070.

في جلسة التنفيذ وافق المالك أيضًا على الخطر المتبقي لاحتمال عدم اكتشاف اسم شخص أو معرّف حساب داخل النص الحر بعد مراجعته المحتوى. لا يُعد ذلك تصريحًا بحفظ بيانات شخصية أو حسابية عمدًا؛ تُرفض المكتشفة، ولا يُدّعى ضمان كشف كامل.

في 2026-11-05 نجحت ستة اختبارات بروتوكول مستقلة باستخدام Node 22.23.1، شملت الصفحات والرفض وغياب القدرة وخطأ العميل والانقطاع. تحقق `codex mcp get` من قراءة إعداد الخادم المؤقت في Codex CLI 0.163.0 دون حفظه؛ لم يُشغّل اختبار العرض على واجهة ذلك العميل، ولا يثبت ذلك دعمها لـ elicitation أو مراجعة المحتوى كاملًا.

**خط أساس التطوير:** checkout على `main`؛ عند الفحص ظهر مجلد `specs/008-site-knowledge/` غير متتبع، ولم تظهر تعديلات أخرى. روجعت حدود الثقة في `scope.ts` و`bridge-connections.ts` و`SECURITY.md`: اختيار profile للتوجيه وليس ACL ضد عميل مقترن يحمل token. أُنشئت نسخة ملفات مؤقتة معزولة دون ملفات env أو مخرجات dist، تستفيد من dependencies الموجودة للقراءة؛ نجح `npm run build` داخل النسخة، ولم يُشغَّل daemon أو Chrome للمستخدم. اختبارات daemon اللاحقة تستخدم fixtures ذات state directory وport مؤقتين.

في النسخة المعزولة نجح `npm test -- tests/memory-daemon-integration.test.ts` بعدد 9 اختبارات باستخدام daemon اصطناعي وامتداد وهمي وstate directory وports مؤقتة؛ هذا اختبار توافق للذاكرة القائمة، وليس تنفيذًا أو اختبارًا لميزة 008.

**تقدم التنفيذ الجزئي:** أضيفت وحدات السجل والنطاق والسياسة والتخزين والمسودات وخدمة داخلية ومسار قراءة داخلي، ولم تُسجّل أدوات معرفة عامة في MCP. أضيف تسلسل مشترك مع سياسة الذاكرة القديمة وسجل durable لحجب الحذف غير المكتمل. يرتبط أمر حذف الذاكرة القديم بهذا السجل عند وجود بيانات معرفة، ويتحقق من المخازن قبل إعلان النجاح؛ الملفات المعزولة غير القابلة للفحص تمنع تأكيد الحذف. الاستكمال بعد restart يحتاج حاليًا إعادة طلب الحذف للنطاق نفسه، والتعافي العام لم يكتمل. تتطلب واجهات الحفظ callbacks داخلية لا تُعد إثبات موافقة مالك. توصيل daemon وMCP وCLI وقناة الموافقة والاستعادة والاستيراد والتكامل الفعلي ما زال مطلوبًا. نجح build وlint وtypecheck و348 اختبارًا مستهدفًا في نسخة معزولة، بالإضافة إلى اختبار حذف الكل الاصطناعي لاحقًا؛ هذا لا يثبت نجاح اختبارات المشروع كلها. لم يكتمل T070 ولم تُؤهّل واجهة للاستخدام الحقيقي.

**فحص قناة الموافقة الحالية:** يستدعي `register-tools.ts` واجهة `elicitInput` بشرط `elicitation.form`، ويرجع `requestOwnerConfirmation` حالة الرفض أو الغياب؛ لا تتضمن هذه الواجهة إثباتًا أن العميل عرض الرسالة كاملة، أو عرض صفحات الاستعادة ومحتواها. لم يُحدد عميل ثبت فيه ذلك بعد، لذا لا تُعلَّم T003 أو T070 كمكتملة ولا يُمكَّن الحفظ الحقيقي. الخطوة التالية هي بناء مسار مراجعة فعلي قابل للاختبار وإثبات عرضه على عميل مالك حقيقي ببيانات اصطناعية، مع متابعة المهام المستقلة بالتوازي المنطقي.

**نقطة الاستئناف:** استكمل T023–T027 وT030–T038، خصوصًا ربط الموافقة الفعلية والنطاق عبر MCP (T075–T077)، وحالات فشل وتعافي الحذف متعددة المخازن. القراءة والبحث المرقمان داخليان فقط، مع ربط cursor بالنطاق والفلتر والنسخة؛ إبراز التعارض واختبارات البحث الشاملة والتصدير والاستعادة والملخص والاستيراد وبوابة واجهة المالك ما زالت غير مكتملة. لا تستخدم الخدمة مع بيانات فعلية أو تفعّل الكتابة قبل اكتمال البوابات والاختبارات.

**أدلة الملخص**: تُقبل الأحداث الفعلية الموثوقة فقط من مسار جلسة يُثبت ربط الحدث ونتيجته ووقته بالنطاق؛ يُفحص وجوده في P3 ولا يُفترض. عند غيابه تبقى معلومات الوكيل `declared` و`unverified`، حتى بعد موافقة المالك على حفظها.

فحص أولي للمصدر: `MemoryService.afterCall` يستقبل نتيجة استدعاء متصفح و`sessionId` و`daemonCallId` وسياقًا اختياريًا، و`OutcomeObserver` يعالج بعض النتائج لأغراض محددة. بنية `MemoryCallOutcome` نفسها لا تحمل وقت الحدث أو حدود مهمة أو إثبات أن هدف المهمة تحقق؛ غياب observation عند الفشل قد يمنع ربطه بموقع موثوق. لذلك لا يُستخدم نجاح استدعاء منفرد كدليل على إصلاح أو اختبار مهمة. هذا فحص جزئي وليس إثباتًا بعدم وجود مصدر آخر؛ T072 تبقى مفتوحة لحين استكمال تتبع الأحداث واختبارها.

## Phased delivery and acceptance

1. **P0 — بوابات ومراجعة مخاطر**: مراجعة التهديدات وواجهة تأكيد تعرض كل المحتوى بلا اقتطاع، والتحقق من العميل الموثوق واختبارين profile. القبول: إثبات مسار الموافقة أو فشل مغلق، وتحديد الحدود التشغيلية؛ لا تُفعّل كتابة إن تعذر الإثبات.
2. **P1 — المعرفة العامة اليدوية**: مخزن مستقل، نطاق profile/origin، CRUD وبحث وتصدير محدود، موافقة جماعية دقيقة ومراجعة المصدر والتعارض. القبول: SC-001–004 وSC-006 وSC-008، بما فيها سباقات الحذف والموافقة ورفض الحسابات الخاصة. لا حفظ تلقائي.
3. **P2 — الاستعادة المدارة**: ملف تصدير محدود وآمن، معاينة لنطاقه وتحذير من إحياء المحذوف، ثم موافقة ذرية لكل موقع/profile. القبول: SC-007، بقاء البيانات دون تعديل عند الرفض أو تلف الملف، ونتيجة صريحة لو تعذرت معرفة نتيجة commit. النسخ الخارجية خارج سيطرة النظام.
4. **P3 — ملخصات المهمة**: إنشاء مقترح غير محفوظ من أحداث المهمة المتاحة بحدودها، ثم مراجعة يدوية بنفس P1. القبول: فصل المنفذ/المخطط/الاختبار وعدم حفظ شيء قبل الاعتماد.
5. **P4 — الاستيراد الاختياري**: مصدر محلي يختاره المالك، parser محدود، معاينة واختيار واعتماد كل دفعة ضمن موقع/profile واحد. القبول: SC-005 وSC-008، ولا إرسال خارجي أو استيراد ضمني.

البيانات الشخصية أو المالية الاختيارية مؤجلة إلى تصميم وسياسة وموافقة منفصلة؛ ليست ضمن P1–P4 تلقائيًا. كل مرحلة تشمل unit/integration/security tests وchecks المشروع، ولا تُطلق تلقائيًا عند اجتياز المرحلة السابقة. معيار الحفظ من نص حر هو قبول مراجعة المالك مع كشف best-effort ومخاطر موثقة؛ ليس ضمانًا تقنيًا مطلقًا. يلزم ترخيص مستقل قبل أي ترحيل بيانات حقيقية أو نشر.

## Rollback and recovery

عطّل الميزة وارفض القراءات والكتابات الجديدة، ثم صفِّ أو ألغِ الطلبات المعلقة. إبقاء مخزن 008 منفصلًا يسمح بالعودة لإصدار لا يعرفه من غير إعادة كتابة `memory/sites` أو `memory/maps`. لا تحذف مخزن 008 عند الرجوع تلقائيًا؛ اتبع سياسة المالك للنسخ والاحتفاظ. الاستعادة المدارة تمر بمعاينة وتحذير وموافقة؛ الاستعادة الخارجية قد تعيد بيانات محذوفة ولا يمكن ضمان منعها. فشل fsync بعد rename يعني `OUTCOME_UNKNOWN` ويستلزم فحص النسخة قبل إعادة المحاولة.
